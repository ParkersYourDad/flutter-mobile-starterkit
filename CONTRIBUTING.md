# Contributing

Thanks for helping improve the Flutter Mobile Starter Kit.

## Before changing code

- Keep the project mobile-only (Android and iOS).
- Preserve English/Arabic localization and LTR/RTL behavior.
- Use centralized theme tokens and shared components; do not add screen-specific arbitrary colors, spacing, radii, or typography.
- Use Riverpod 3 `Notifier`/`AsyncNotifier` patterns for new stateful features. Do not introduce `StateProvider` or `StateNotifierProvider` in new code.
- Keep dependencies minimal. A new direct dependency needs a concrete requirement, current SDK compatibility, maintenance review, and license compatibility.
- Do not introduce placeholder functionality, credentials, private signing material, or sensitive logs.

## Local validation

Run from the repository root:

```sh
flutter pub get
flutter gen-l10n
dart format --output=none --set-exit-if-changed .
flutter analyze --fatal-infos
flutter test --reporter expanded
```

For relevant platform changes, validate the Android debug build on a system with the Android toolchain and the iOS simulator build on macOS with Xcode. GitHub Actions runs those two build jobs for code-relevant changes.

## Localization

- Add user-facing strings to both ARB files under `lib/l10n/arb/`.
- Do not edit files under `lib/l10n/generated/`; they are generated by `flutter gen-l10n`.
- Verify translated labels, mixed Arabic/Latin text, directional icons, and back navigation.
- Keep semantics labels and error messages localized.

## Shared UI and tests

- Prefer extending an existing shared component over adding a near-duplicate.
- Add focused unit/widget tests for new behavior and error paths.
- Update a golden only when an intentional visual contract changes. Review the image diff before committing it.
- Test Light/Dark and Arabic/English where the changed code affects theme or directionality.
- Never say a check passed unless the command or CI result confirms it.

## Pull requests

A pull request should:
- Explain the user-facing or engineering problem being solved.
- State any design/architecture decisions and their trade-offs.
- Include relevant tests and document checks that could not be run.
- Confirm no secrets, generated clutter, unused dependencies, fake behavior, or unrelated changes are included.
- Keep scope focused; avoid broad refactors without a concrete need.
